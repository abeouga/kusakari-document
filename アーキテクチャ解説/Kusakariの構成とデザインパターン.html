フロントエンドとバックエンド

何をするものか

フロントエンドは、ブラウザーの中で動いて画面を作るプログラムです。Kusakari では JavaScript で書いています。バックエンドは、サーバーで動いてデータを検査し、データベースを読み書きするプログラムです。EC は Java、Canvas は Python で書いています。

2つは別々のプログラムで、HTTP で通信します。バックエンドのうち、フロントエンドから呼ばれる窓口を API と呼びます。

行き来するものの中身

向き名前入っているもの例
画面 → サーバーHTTP リクエストメソッド、URL、(あれば)本文PUT /api/cart/items/olive
本文 {"quantity": 2, "revision": 3}
サーバー → 画面HTTP レスポンスステータスコード(結果を表す3桁の数字)、本文200
本文は下の JSON

JSON は、データを文字で書く形式です。{ } が「名前と値の組の集まり」、[ ] が「並び」です。カートを読んだときのレスポンスは、次の形をしています(項目名は実物、値は例です。一部を省いています)。

  "storeName": "Kusakari 東京店",

なぜ2つに分けるのか

  • 別々に直せる。ボタンの位置を変えるときにサーバーのコードを触らず、在庫の計算を変えるときに画面のコードを触りません。
  • 同じ API を複数の画面から使える。EC の GET /api/cart は、EC の画面だけでなく Canvas の画面からも呼ばれています(6章)。
  • 正しさをサーバーで守れる。ブラウザーの中のプログラムは利用者が書き換えられます。価格・在庫・合計金額は、必ずサーバーが計算し直します。

開発中は、サーバーが2つ動く

開発中は、プロジェクトごとに2つのサーバーが動きます。画面のファイルを配るサーバー(Vite)と、API のサーバーです。ブラウザーは Vite のアドレスだけを開き、/api で始まる URL は Vite が API のサーバーへ中継します。

REST API

何をするものか

REST は、API の URL の決め方です。URL で「何を」扱うかを表し、HTTP メソッドで「どうするか」を表します。URL には動詞を入れず、cart(カート)、orders(注文)、gardens(庭)のような名詞を使います。

メソッド意味本文
GET読む。データは変えないなし
POST新しく作る。または処理を実行する作るものの内容
PUT指定した内容に置き換える置き換えた後の内容
PATCH一部だけ変える変える項目
DELETE消すなし

実際の API

Kusakari の API から、4章・5章で出てくるものを抜き出しました。{id} のように { } で囲んだ部分は、そこに実際の値が入ることを表します(例: /api/gardens/3f2a…)。

プロジェクトメソッドと URLすること

  • 「画面とサーバーの約束」が、メソッド・URL・本文の表として書けます。Kusakari では docs/api.md(EC)と docs/architecture.md(Canvas)に書いています。

3層アーキテクチャ

何をするものか

バックエンドのコードを、役割で3つに分ける書き方です。リクエストは、Controller → Service → Repository の順に進み、結果は逆の順に戻ります。

層受け持つことしないこと
ControllerHTTP の入口。どの URL でどの関数を呼ぶかを決め、入力を受け取り、結果を返す業務の判断、SQL
Service業務のルール。在庫は足りるか、金額は合っているか、どの順番で保存するかHTTP の細かい扱い
Repositoryデータベースの読み書き業務の判断

一緒に出てくる2つの言葉: DTO と Entity

  • DTO(Data Transfer Object)は、API の入力・出力の形を表すクラスです。JSON の項目と1対1に対応します。
  • Entity は、データベースのテーブルの1行を表すクラスです。テーブルの列と1対1に対応します。

似たクラスを2種類持つのは、テーブルの形と API の形を別々に変えられるようにするためです。テーブルに内部用の列を足しても、API のレスポンスには出ません。逆に、画面のために「合計金額」のような計算結果を DTO に足しても、テーブルは変わりません。

なぜ3つに分けるのか

  • 直す場所が1か所に決まる。「URL を変える」なら Controller、「在庫不足の条件を変える」なら Service、「検索の SQL を速くする」なら Repository です。
  • 同じ処理を使い回せる。EC の CartService は、カートの API(CartController)からも、庭の買い物リストの処理(ShoppingService)からも、注文の処理(CheckoutService)からも呼ばれます。
  • 読む範囲が狭くなる。在庫のルールを知りたいとき、HTTP や SQL のコードを読まずに済みます。

React

何をするものか

React は、画面を部品(コンポーネント)の組み合わせで作るための JavaScript のライブラリです。覚える言葉は、コンポーネント・state・hook の3つです。

コンポーネント = 画面の一部を返す関数

kusakari-canvas/frontend/src/pages/App.jsx
export function App() {1
    const path = canvasPathname();
    // …(省略)
    const match = path.match(/^\/gardens\/([^/]+)\/?$/);2
    const gardenId = match ? decodeURIComponent(match[1]) : null;
    return <AuthGate>{gardenId ? <EditorPage gardenId={gardenId}/> : <GardenListPage />}</AuthGate>;3
}
  1. App はふつうの JavaScript の関数です。React では、画面の一部を返す関数をコンポーネントと呼び、名前を大文字で始めます。
  2. ここもふつうの JavaScript です。URL のパスが /gardens/〇〇 の形なら、〇〇 の部分を gardenId に取り出します。
  3. return の後ろの、HTML に似た部分を JSX と呼びます。読み方は3つです。
    • <EditorPage gardenId={gardenId}/> は、「EditorPage 関数を、引数 { gardenId: gardenId } で呼び、返ってきた画面をここに置く」という意味です。この引数を props と呼びます。
    • { } の中には JavaScript の式を書けます。ここでは 条件 ? A : B で、庭の ID があれば編集画面、なければ一覧画面を選んでいます。
    • <AuthGate>…</AuthGate> のように囲むと、中身が AuthGate に children という名前の引数で渡ります。

JSX を含むファイルは、拡張子を .jsx にしています。

  2. ボタンが押されたら setViewMode('3d') を呼びます。
  3. setViewMode が呼ばれると、React は EditorPage 関数をもう一度実行します。今度は viewMode が '3d' なので、3D の画面(GardenCanvas)が選ばれます。

FastAPI と Spring Boot

何をするものか

どちらも、バックエンドを作るための道具(フレームワーク)です。することは同じで、「この URL に、この HTTP メソッドでリクエストが来たら、この関数を呼ぶ」という対応を登録し、関数の戻り値を JSON にして返します。FastAPI は Python 用、Spring Boot は Java 用です。

FastAPI の最小の形

kusakari-canvas/backend/kusakari_canvas_api/main.py
@router.get("/api/gardens", response_model=list[GardenSummary])1
def gardens(db: Db, owner: Owner):2
    return service.list_gardens(db, owner)3
  1. @ で始まる行はデコレーターといい、すぐ下の関数に働きを付け足す Python の書き方です。@router.get("/api/gardens") は、「GET /api/gardens が来たら、下の関数を呼ぶ」と登録します。response_model は、戻り値をどの形の JSON にするかの指定です。ここでは GardenSummary の並びです。
  2. 引数の db(データベース接続)と owner(ログインしている会員の ID)は、FastAPI が用意して渡します。用意の仕方は5章で説明します。
  3. 戻り値がそのままレスポンスになります。ここでは Service の関数を呼んで、結果を返すだけです。

Spring Boot の最小の形

kusakari-ec/backend/src/main/java/jp/kusakari/ec/commerce/controller/CartController.java
@RestController1
@RequestMapping("/api/cart")2
@RequiredArgsConstructor3
public class CartController {

  private final CartService carts;
  private final CartSessionResolver sessions;

  @GetMapping4
  public CartView get(HttpServletRequest request, HttpServletResponse response) {
    return carts.read(sessions.resolve(request, response));5
  }
  // …(省略)
}
  1. @ で始まる行はアノテーションといい、クラスやメソッドに付ける目印です。Spring Boot は起動するときに目印の付いたクラスを探し、目印に応じた準備をします。@RestController は、「このクラスは HTTP の入口。メソッドの戻り値は JSON にして返す」という目印です。
  2. このクラスの中の URL は、すべて /api/cart で始まります。
  3. final の付いたフィールド(carts と sessions)を引数に取るコンストラクターを、自動で作ります。CartService のオブジェクトは Spring Boot が作って渡すので、このクラスに new CartService(...) は出てきません(4章の DI)。
  4. GET /api/cart が来たら、下のメソッドを呼びます。
  5. 戻り値の CartView が JSON になります。ここでも、Service のメソッドを呼んで結果を返すだけです。引数の request と response は、届いた HTTP リクエストと、これから返す HTTP レスポンスを表すオブジェクトです。誰のカートかを調べる sessions.resolve に、そのまま渡しています。

Kusakari は、利用者から見ると1つのサイトです。開発の上では、EC と Canvas の2つに分かれていて、それぞれが画面・API・データベースを持っています。

どのデータをどちらが持つかは、はっきり分けています。相手が持つデータが必要なときは、相手のデータベースを読まずに、相手の API を呼びます。

分け方の考え: 機能で縦に切り、その中を層で横に切る

jp/kusakari/ec/ の直下は機能の名前です。その下は層(3層 + DTO + Mapper)の名前です。docs/architecture.md には、「機能単位に分け、その中で controller / service / persistence / dto / mapper を分離する」と書かれています。

分け方こうしている理由
1段目を機能にする「カートを直したい」ときに commerce/ を開けば、入口から DB まで関係するファイルがそろっています。関係のない機能のファイルが目に入りません。
2段目を層にするフォルダー名を見れば、そのファイルが HTTP を扱うのか、業務のルールなのか、DB を扱うのかが分かります。
common/ を別にするエラーの返し方や接続元の確認は、特定の機能のものではありません。どの機能からも同じものを使います。
db/migration/ を resources/ に置くテーブル定義(SQL)は Java のコードではないため。アプリと一緒に配り、起動のときに未適用のものを順番に実行します。

表どおりでない所

  • auth/ と shopping/ は、層のフォルダーを作らず、クラスを直接置いています。理由は docs に書かれていません。クラス名の末尾(AuthController、AuthService、AuthMemberRepository)で層が分かります。
  • 店舗のテーブルを表す StoreEntity と StoreRepository は、store/ ではなく catalog/persistence/ にあります。store/ にあるのは、店舗プロフィールの編集と出店申請です。
  • commerce/ には session/ があります。リクエストから「その人のカート」を求める CartSessionResolver が入っています。

2. DTO: 入力の形

backend のデザインパターン

デザインパターンは、よくある問題に対する、名前の付いた解き方です。EC の backend で使われているものを、「何か」「どこにあるか」「なぜ使うか」で説明します。

1. レイヤード(層に分ける)

何か
コードを Controller・Service・Repository の層に分け、上の層から下の層だけを呼ぶ。
どこにあるか
各機能の controller/ service/ persistence/。カートの例がそのままこの形です。
なぜ使うか
直す場所が1か所に決まり、同じ Service を複数の入口から使い回せるため。

2. DI(依存性の注入)

何か
クラスが使う相手のオブジェクトを、自分で new せず、外から受け取る書き方。
どこにあるか
ほぼすべてのクラス。@RequiredArgsConstructor と private final CartService carts; の組み合わせがそれです。Spring Boot が、@Service などの目印が付いたクラスのオブジェクトを作り、コンストラクターに渡します。
なぜ使うか
CheckoutService は10個以上のクラスを使います。それぞれの作り方(何を渡して new するか)を、使う側が知らなくて済みます。作る順番も Spring Boot が決めます。

3. DTO と Mapper

何か
API の形を表すクラス(DTO)を Entity と別に持ち、Entity から DTO への詰め替えを専用のクラス(Mapper)に任せる。
どこにあるか
DTO は catalog/dto/CatalogDtos.java と commerce/dto/CommerceDtos.java に、record でまとめて書かれています。Mapper は ProductMapper と OrderResponseMapper です。
なぜ使うか
テーブルの形と API の形を別々に変えるため(2章)。詰め替えを1か所に集めると、項目を足すときに直す場所が1つで済みます。

  2. 名前が違うものや、計算が要るものだけ、@Mapping で指定します。

4. Repository

何か
DB の読み書きを、「探す」「保存する」「消す」というメソッドを持つオブジェクトにまとめる。使う側は SQL を書かない。
どこにあるか
各機能の persistence/repository/。Spring Data JPA を使い、interface だけを書きます。
なぜ使うか
Service が「何を保存するか」に集中でき、SQL の書き方やロックの条件が1か所に集まるため。

5. Filter(入口で必ず通る処理)

何か
リクエストが Controller に届く前に、必ず通る処理。条件に合わなければ、Controller を呼ばずにエラーを返す。
どこにあるか
通る順番は、LocalApiFilter(接続元の確認)→ Spring Security(ログインと、書き込みの確認用の値の検査)と SessionValidityFilter(ログインの期限)→ Controller です。
なぜ使うか
「ログインしているか」をすべての Controller のメソッドに書くと、書き忘れが起きます。入口に1回書けば、全部の API に効きます。

6. 例外の一元処理

何か
エラーを例外として投げ、例外をレスポンスに変える処理を1か所に集める。
どこにあるか
Service は throw new ApiException(409, "OUT_OF_STOCK", "…") と投げるだけです。ApiErrors が受け取って JSON にします。
なぜ使うか
エラーの形({code, message})が全部の API でそろいます。Service は、HTTP のレスポンスの作り方を知らなくて済みます。

  3. 例外が持っているステータスコードと、{code, message} の本文でレスポンスを作ります。

7. 同時更新への備え(版番号とロック)

何か
2つの操作が同じデータを同時に変えようとしたときに、片方の変更が黙って消えるのを防ぐ。
どこにあるか
版番号: カートは revision を持ち、変更のたびに1つ増えます。画面は、読んだときの revision を変更のリクエストに付けます。DB の値と違えば、checkRevision が 409 を返します。
ロック: findLocked で行をロックし、確認から保存までの間に割り込まれないようにします。CheckoutService は、店舗 → 商品 → 在庫の順に、ID の小さい順でロックします。
なぜ使うか
2つのタブで同じカートを開いて数量を変えたとき、後から押した方に「カートが更新されました」と知らせるため。同じ在庫の最後の1個を2人が同時に注文したとき、2人とも成功しないようにするため。ロックの順番を決めておくのは、2つの注文が互いのロックを待ち続けて止まるのを防ぐためです。

8. 冪等キー(同じ注文を2回作らない)

何か
リクエストに、画面が作った一意の ID を付ける。サーバーは、同じ ID のリクエストが2回届いても、処理を1回しか行わない。
どこにあるか
注文のリクエストの requestId。画面(useShop.js)が crypto.randomUUID() で作ります。CheckoutService.placeOrder は、最初に orders.findByCartIdAndRequestIdOrderByStoreIdAsc で同じ ID の注文を探し、あれば新しく作らずにそれを返します。
なぜ使うか
通信が途中で切れると、画面は「注文できたのか」が分かりません。同じ requestId で送り直せば、できていた場合は同じ注文が返り、できていなかった場合だけ新しく作られます。

9. 外部 API の窓口クラス

何か

どこにあるか

3. 状態は上で持ち、props で下へ渡す

4. URL と画面の対応を自分で書く

何か

なぜ使うか

5. 「読む → 操作する → 読み直す」の hook(useResource.js)

何か
API のパスを渡すと、読み込んだデータ・エラー・処理中かどうかと、「操作を実行して、終わったら読み直す」関数を返す hook。

なぜ使うか
管理の画面はどれも同じ流れなので、流れを1回だけ書いて使い回します。操作の後に必ずサーバーから読み直すので、画面が古い内容のまま残りません。

6. イベントで知らせる

何か
「起きたこと」を名前の付いたイベントとして発信し、関心のある部品が受け取る。発信する側は、誰が受け取るかを知らない。
どこにあるか

なぜ使うか
どの画面のどの通信で期限切れが起きても、同じ案内を出せます。通信のコード(api.js)が、画面の部品を直接呼ばずに済みます。

  • 14: Entity をそのまま返さず、DTO(ProductView)に詰め替えます。このとき、在庫の数と公開状態を商品に合わせます。

  • 19〜20: Service のメソッドを抜けると、トランザクションが確定します。cart_items の行と、carts.revision の +1 が、まとめて保存されます。

注文を確定する

  • 4〜5: 画面は、requestId(冪等キー)と、利用者が見ていた revision と合計金額(expectedTotalYen)を送ります。価格そのものは送りません。

  • 12〜15: 在庫をロックしてから、サーバーが在庫と合計金額を計算し直します。画面が見ていた金額と違えば、注文せずに 409 を返します。
  • 16〜19: 注文の保存、在庫の減算、カートを空にする、の3つは同じトランザクションです。どれか1つでも失敗すれば、3つとも起きなかったことになります。「在庫は減ったが注文がない」という状態になりません。

  1. useQuery(TanStack Query というライブラリの hook)は、queryFn を実行してサーバーから読み、結果(data)、読み込み中かどうか(isLoading)、失敗したかどうか(isError)を返します。queryKey は結果に付ける名前で、同じ名前の結果は覚えておいて使い回します。
  2. 読めたら、ストアに渡します。hydrate は、受け取った庭のコピー(structuredClone(document))を作って、ストアに置きます。
なぜ使うか
サーバーから読んだ値は「最後に保存した状態」、ストアの値は「編集中の状態」で、意味が違います。コピーを編集するので、保存に失敗しても、最後に保存した状態は手元に残ります。庭の一覧(GardenListPage)のように、読むだけで編集しない画面は、useQuery だけを使い、ストアを使いません。

4. 自動保存(useGardenAutosave.js)

何か
保存ボタンを押さなくても、変更があれば保存する hook。
どこにあるか
hooks/useGardenAutosave.js。次の3つの工夫があります。
  • 0.5秒待つ。isDirty が true になると、window.setTimeout(() => { void save(); }, 500) で予約します。その間に次の編集があれば、予約を取り消して、やり直します。ドラッグで動かしている途中は、1回も送りません。
  • 保存を重ねない。保存の途中(inFlight.current がある間)は、新しい保存を始めません。
  • 保存中の編集を消さない。保存が終わったとき、markSaved(saved, submitted) が、送った庭と今の庭を比べます。違っていれば、今の庭を残して版番号だけを進め、isDirty を true のままにします。続けてもう一度保存されます。
なぜ使うか
3D の編集では、細かい操作が続きます。操作のたびに送ると通信が多すぎ、ボタンを押すまで送らないと保存し忘れが起きるためです。

ログインを共有する仕組み

ログインの仕組みを持っているのは EC だけです。Canvas は、EC のログインをそのまま使います。

  1. 利用者が EC でログインすると、EC API は KUSAKARI_SESSION という名前の Cookie をブラウザーに渡します。Cookie は、サーバーがブラウザーに預ける小さな値で、ブラウザーは同じサーバーへのリクエストに毎回付けて送ります。
  2. 開発中は、EC も Canvas も同じ 127.0.0.1 で動いています。Cookie はポート番号を区別しないので、ブラウザーは Canvas へのリクエストにも同じ Cookie を付けます。
  3. Canvas API(auth.py)は、受け取った Cookie をそのまま付けて、EC API の GET /api/auth/me(書き込みのときは POST /api/auth/verify)を呼びます。
  4. EC API が返した会員の ID を、Canvas API は庭の持ち主(gardens.owner_id)として使います。

EC API が Canvas API を呼ぶとき(図12 の 3)も同じで、CanvasClientConfiguration が、利用者の Cookie を Canvas へのリクエストに引き継ぎます。Canvas API は、それをまた EC に見せて確かめます。こうすると、Canvas は「EC から来たリクエストだから信用する」という特別な扱いをせず、いつも同じ方法で本人を確かめられます。

やり取りする値の決まり

  • 相手のデータベースを読まない。必要なものは、相手の API を呼んで受け取ります。相手のテーブルの形が変わっても、API の形が同じなら影響を受けません。
  • 渡すのは ID と数量だけ。Canvas から EC へは、商品の ID(productId)、素材のコード(materialCode)、数量(quantity)、単位(unit)を渡します。3D の部品そのものや、価格は渡しません。
  • 商品・価格・在庫・カート・注文は、EC が正しい値を持つ。Canvas の画面に出す商品の一覧や価格は、そのつど EC API から読みます。

共通ヘッダー

画面の上のヘッダー(ロゴ、ナビゲーション、カートの件数)は、EC と Canvas で同じ部品(@kusakari/site-header)を使っています。元のコードは EC の packages/site-header/ にあります。変更したら npm pack で1つのファイル(.tgz)にまとめ、Canvas の vendor/ に置きます。Canvas は、そのファイルを部品として読み込みます。

コードをコピーして2か所で直す形にしないのは、片方だけ直して見た目がずれるのを防ぐためです。部品には番号(バージョン)が付いているので、Canvas がどの版を使っているかが frontend/package.json で分かります。
