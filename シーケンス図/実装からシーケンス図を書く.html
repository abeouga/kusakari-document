1. 実装から書くとは

シーケンス図は、ふつう実装の前に書きます。図で処理の順番を決め、そのとおりにコードを書きます。Kusakari は順番が逆なので、図の役割も変わります。

設計から書く(ふつうの順番)

  • これから作る処理を決めるために書く
  • クラス名や関数名は自分で考える
  • 図が正しく、コードを図に合わせる

実装から書く(今回)

  • すでにある処理を写すために書く
  • クラス名や関数名はコードから拾う
  • コードが正しく、図をコードに合わせる

矢印1本は、コードの1か所に対応させます。矢印を引くたびに「どのファイルの、どの関数が、何を呼んでいるか」を言える状態にします。言えない矢印は、想像で書いた矢印です。

この資料で作る図

ユースケースごとに2枚作ります。先に概要図で全体をつかみ、次に詳細図でファイルの流れを追います。

種類縦線(ライフライン)矢印に書くこと使いどころ
概要図層ごとに1本。画面、API、DB、外部システムHTTP のメソッドとパス、DB への操作を日本語でユースケース記述と見比べる。レビューで全体を説明する
詳細図ファイルごとに1本。コンポーネント、フック、Controller、Service、Repository実際の関数名と API 名コードを直す人が、どのファイルを通るかを知る

画面 React の読み方

コードの書き方意味図では
export function CategoriesPage() { … return (<form>…</form>); }コンポーネント。画面の部品を返す関数。return の中の HTML に似た部分が画面になるライフライン1本
onClick={…}、onSubmit={save}利用者が操作したときに呼ばれる関数アクターからの矢印の行き先
const [editing, setEditing] = useState('')画面が覚えておく値。setEditing(…) で値を変えると、画面が描き直される自分への矢印、またはアクターへの「表示」
useResource(…)、useShop() など use で始まる関数フック。複数の画面で使う処理をまとめた関数。通信はここに入っていることが多いライフライン1本
useEffect(() => { … }, […])、useQuery({ … })画面が表示されたときに自動で実行される処理操作なしで始まる矢印
await request(…)、await fetch(…)サーバーへの HTTP リクエスト。応答が返るまで次の行に進まない層をまたぐ矢印

3. 図にする10の手順

例1の EC-A07「商品カテゴリを追加する」を使って、手順を1つずつ説明します。完成した図は例1にあります。

  1. ユースケース記述を「操作」と「応答」に分ける

    基本フローの各ステップを、だれが主語かで分けます。「運営者が」で始まる文はアクターからの矢印になります。「システムが」で始まる文は、画面だけで済むのか、サーバーまで行くのかをコードで確かめます。

    番号基本フロー(EC-A07)主語コードで確かめること
    1メニュー「カテゴリ管理」を開く運営者どのコンポーネントが表示されるか
    2入力欄、ボタン、カテゴリ一覧を表示するシステム一覧はどこから取ってくるか
    3カテゴリ名を入力する運営者入力のたびに通信するか(しないなら図に書かない)
    4「保存」ボタンをクリックする運営者どの関数が呼ばれるか
    5カテゴリ名を検証するシステム検証は画面とサーバーのどちらにあるか
    6追加し、「保存しました。」を表示し、一覧を更新するシステム保存のあと、一覧をどう取り直すか

  2. 画面の文言で検索して、入口のファイルを見つける

    ユースケース記述には、ボタン名やメッセージが「」付きで書かれています。その文言をプロジェクト全体で検索します。VS Code なら Ctrl+Shift+F、ターミナルなら git grep -n "編集を取消" です。

    「編集を取消」で検索すると OperatorPages.jsx が見つかります。メニュー名の「カテゴリ管理」で検索すると Workspace.jsx が見つかり、パスと画面の対応が分かります。

    // kusakari-ec/frontend/src/workspace/Workspace.jsx
['/operator/categories', 'カテゴリ管理', Tags],                          // 31行目 メニューの定義
else if (path === '/operator/categories') content = <CategoriesPage />;   // 142行目 パスと画面の対応
    探したいもの検索する言葉Kusakari での例
    入口の画面ボタン名、見出し「受取準備完了にする」→ PickupOrders.jsx
    メニューと画面の対応メニュー名「カテゴリ管理」→ Workspace.jsx

  3. 操作から、呼ばれる関数をたどる

    コンポーネントの return の中で、onSubmit や onClick を探します。そこに書かれた関数が、操作の入口です。「保存」ボタンは <form> の中にあるので、クリックすると onSubmit の save が呼ばれます。

    // kusakari-ec/frontend/src/workspace/OperatorPages.jsx(抜粋)
export function CategoriesPage() {
  const resource = useResource('/categories');          // 画面を開いたときに一覧を取る(手順4で読む)
  const [editing, setEditing] = useState('');

  async function save(e) {                              // 「保存」で呼ばれる
    e.preventDefault();
    const form = e.currentTarget;
    if (await resource.run(() => write('/operator/categories', 'PUT', { previous: editing, name: values(form).name }))) {
      setEditing('');
      form.reset();                                     // 成功したら入力欄を空にする
    }
  }

  return (
    <form onSubmit={save}>                              // 操作と関数の対応
      <Input label="カテゴリ名" name="name" value={editing} maxLength={30} />
      <button disabled={resource.busy}>保存</button>

  4. HTTP のメソッドとパスを特定する

    save の中に fetch はありません。resource.run(…) と write(…) を呼んでいるので、その定義を開きます。関数名を Ctrl を押しながらクリックすると定義に移動できます。

    // kusakari-ec/frontend/src/workspace/useResource.js(抜粋)
async function run(action, message = '保存しました。') {
  try {
    await action();          // 渡された write(...) を実行する
    await reload();          // 成功したら一覧を取り直す(GET)
    setNotice(message);      // 「保存しました。」
    return true;
  } catch (reason) {
    if (reason instanceof ApiError && [404, 409].includes(reason.status)) await reload();
    setError(reason instanceof Error ? reason.message : '処理を完了できませんでした。');
    return false;
  }
}
export const write = (path, method, body) => request(path, method, JSON.stringify(body));

// kusakari-ec/frontend/src/api.js(抜粋)
export async function request(path, method = 'GET', body) {
  const response = await send(`/api${path}`, { method, body, headers: { 'Content-Type': 'application/json' } });
  return readResponse(response);
}

    ここで3つのことが分かります。

    • 送るのは PUT /api/operator/categories。/api は api.js が付け足している
    • 成功すると reload() が続けて GET /api/categories を送る。1回の「保存」で通信は2回
    • 失敗すると catch に入り、メッセージが setError で画面に出る

  5. パスで検索して、サーバーの受け口を見つける

    パスの後半 /operator/categories をバックエンドのフォルダーで検索します。@PutMapping の付いたメソッドが受け口です。

    // kusakari-ec/backend/.../catalog/controller/CategoryController.java
public record Input(@NotNull @Size(max = 30) String previous, @NotBlank @Size(max = 30) String name) {}

@PutMapping("/api/operator/categories")
public Map<String, Boolean> save(@Valid @RequestBody Input in) {   // @Valid が Input の条件を検査する
  service.save(in.previous(), in.name());                          // 次の矢印
  return Map.of("saved", true);                                    // 戻りの矢印 200 {"saved": true}
}

    パス全体で検索して見つからないとき。クラスに @RequestMapping("/api/orders")、メソッドに @PostMapping と、パスが2か所に分かれていることがあります(OrderController)。FastAPI でも APIRouter(prefix="/api/gardens/{id}/image-history") と @router.post("") に分かれます(history_routes.py)。後ろの部分だけで検索し直します。

  6. Controller から奥へ、1行ずつたどる

    Service のメソッドを上から読み、各行を次の3種類に分けます。

    • ほかのファイルを呼ぶ行。矢印になる
    • if と throw の行。分岐になる
    • それ以外の行。変数の計算など。必要なら自分への矢印、不要なら書かない
    // kusakari-ec/backend/.../catalog/service/CategoryService.java(抜粋)
public void save(String previous, String input) {
  auth.requireAdmin();                                             // 矢印 → AuthService
  String name = input.trim();                                      // 自分の処理
  if (name.isEmpty()) throw new ApiException(400, "INVALID_CATEGORY", "カテゴリ名を入力してください。");
  if (name.equals(previous)) return;
  var existing = categories.lock(name);                            // 矢印 → CategoryRepository → DB
  if (existing.filter(CategoryEntity::isAvailable).isPresent()) throw new ApiException(
    409, "CATEGORY_EXISTS", "同じカテゴリがあります。"             // 分岐 5b
  );
  ...
  var target = existing.orElseGet(() -> new CategoryEntity(name));
  target.setDeletedAt(null);
  categories.saveAndFlush(target);                                 // 矢印 → CategoryRepository → DB
  ...
}

    Repository はインターフェースなので、中身の処理はありません。メソッド名とアノテーションから、どんな SQL かを読み取ります。@Lock(PESSIMISTIC_WRITE) は SELECT ... FOR UPDATE(ほかの処理が同じ行を変えられないようにして読む)です。

    コードにあっても、この経路では通らない行があります。name.isEmpty() の検査は、空白だけの入力を止めるように見えます。しかし Controller の @NotBlank が先に止めるので、空白だけの入力は Service まで届きません。画面に出るのは ApiErrors.invalid() の「入力内容・文字数・数値の範囲を確認してください。」です。ユースケース記述の 5a もこの文言になっています。文言で検索して見つけた行は、そこまで処理が届くかを必ず確かめます。

  7. 戻り道をたどる

    行きの矢印を書き終えたら、同じ道を逆に戻ります。成功の戻り道と、失敗の戻り道の両方を確かめます。

    成功のとき

    CategoryService.save() が終わる → CategoryController が {"saved": true} を返す → api.js の request() がデータを返す → useResource.js の run() が reload() と setNotice() を実行する → CategoriesPage が form.reset() する。

    失敗のとき

    throw された例外を、だれが受け取るかを探します。ApiException.class で検索すると ApiErrors.java が見つかります。

    // kusakari-ec/backend/.../common/web/ApiErrors.java(抜粋)
@RestControllerAdvice                                    // すべての Controller の例外をここで受け取る
public class ApiErrors {
  @ExceptionHandler(ApiException.class)
  public ResponseEntity<ErrorView> business(ApiException error) {
    return ResponseEntity.status(error.status()).body(new ErrorView(error.code(), error.getMessage()));
  }
  @ExceptionHandler({ MethodArgumentNotValidException.class, ... })   // @Valid の違反
  public ResponseEntity<ErrorView> invalid(Exception error) {
    return ResponseEntity.badRequest().body(new ErrorView("INVALID_INPUT", "入力内容・文字数・数値の範囲を確認してください。"));
  }
}

// kusakari-ec/frontend/src/api.js の readResponse()(抜粋)
if (!response.ok) throw new ApiError(data?.message || failure, response.status, data?.code ?? '', data);

    サーバーの例外は、エラーの JSON になってブラウザーに届きます。api.js がそれを JavaScript の例外(ApiError)に変え、手順4で読んだ run() の catch が受け取ります。

  9. 書かないものを決める

    コードの呼び出しをすべて書くと、図は読めなくなります。次の線引きで減らします。

    書く書かない
    概要図アクターの操作、画面の表示、HTTP、DB への操作、外部システムとのやりとり、エラーの種類ファイル名、関数名、画面の中だけの処理
    詳細図ほかのファイルへの呼び出し、HTTP、DB、分岐の原因になる検査(権限、状態、入力)、例外の受け渡しgetter と setter、JSON の形を表すだけのクラス(DTO)、変換だけのクラス(Mapper)、見た目(CSS)、ログ

    迷ったら「この矢印を消すと、ユースケース記述のどれかのステップを説明できなくなるか」で決めます。説明できなくなるなら残します。

    省略した場所には、ノートで「図では省略」と書きます。黙って省くと、読む人は「呼んでいない」と受け取ります。

  10. ユースケース記述と突き合わせる

    最後に、図とユースケース記述を並べて確かめます。

    • 基本フローのすべての番号が、図のどこかに対応しているか
    • 対象にした代替フロー(サーバーが関わるもの)が、alt の枝になっているか
    • 図にあって、ユースケース記述にない処理は何か。権限の確認やロックは書かれていなくて構いません。実装の事実として図に残します
    • ユースケース記述にあって、コードに見つからない処理は何か。見つからなければ、図は実装どおりに書き、差をメモしてチームに伝えます
