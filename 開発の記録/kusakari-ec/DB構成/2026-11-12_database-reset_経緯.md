# EC の DB を初期化して作り直す（issue #106）（経緯）

元の場所：kusakari-ec/docs/database-reset.md（コミット a9cbd69 時点）

### 2026-11-16 の変更：保護をやめ、実行するだけで成功するようにした

ユーザーの判断で、使う人に操作させる処理と、対象を確かめて止まる処理をやめた。ほかの PC では「`git pull` → `DB-reset.bat`」だけで済むようにするため。

- 外したもの：確認の文字（`RESET kusakari`）の入力、Windows の管理者への切り替え、ポートを待ち受けるプロセス・MySQL のポート・データの場所・専用の MySQL の記録との照合、マイグレーション履歴のない DB で止めること、権限（`CREATE` と `DROP`）を先に確かめること、ほかのプロセスが接続していると止めること、バックアップの失敗で止めること
- 代わりにすること：ほかのプロセスの接続は、作り直す前に切る（`KILL`）。バックアップに失敗したら、表示してバックアップなしで続ける。Web と API を止めること、`npm install`、API のビルドは、スクリプトが先に行う
- 残したもの：消す DB の名前を `kusakari` と `kusakari_e2e` に固定すること（`.env` の書き間違いでほかの DB を消さないため）、同じフォルダーで `setup.bat` と同時に実行したときに止めること（2つが同時に DB を作り直すと壊れるため）

### 決めたこと（#106 の「決めること」と、2026-11-16 の変更）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| E2E 用の DB も一緒に初期化するか | する。開発用と E2E 用を必ず一緒に作り直す | 2つの DB は同じマイグレーションで作るもので、セットアップも両方を確かめている。片方だけ古い構成が残ると、E2E が失敗する |
| 確認の方法 | 確認しない（2026-11-16 に変更）。以前は確認の文字（`RESET kusakari`）の入力を求めていた | 実行するだけで成功してほしい（ユーザー判断）。対象を確かめるだけなら `-DryRun` を使う |
| Windows の管理者権限が必要か | 必要としない（2026-11-16 に変更）。以前は管理者として起動し直していた。DB の操作はアプリ用の DB ユーザーで行い、MySQL の管理者（root）のアカウントは聞かない | Windows の確認の操作を減らすため（ユーザー判断）。DB の操作そのものは、セットアップがアプリ用のユーザーに付けている権限（2つの DB への `CREATE` と `DROP`）で足りる。権限が2つの DB に限られているので、ほかの DB を消すことができない |
| Canvas の初期化と一度に実行できるようにするか | しない。EC と Canvas のスクリプトを続けて実行する | Canvas は別のリポジトリで、置き場所が PC によって違う |

## Consequences（日付のある記録）

- 閉鎖した店舗の連絡先を消すイベントは、#107 ではマイグレーションに入れなかった（`docs/database-v3-check/store-closure-event.sql`）。2026-11-12 の決定（3-1）で、イベントをやめてアプリ内の定期処理（1日1回）にした（#79）。セットアップが付ける権限は変えない
- 初期化の後の確認は、`backend/target` にある API の JAR でマイグレーションを適用する。古い JAR のままだと、古いマイグレーションが空の DB に適用されてしまう。2026-11-16 からは、`DB-reset.bat` が初期化の前に API を作り直す
- 2026-11-12、v3 への切り替えの後、以前にビルドしたフォルダーで初期化すると、確認が「Found more than one migration with version 1」で失敗した。Maven の `package` が、ソースから消した旧マイグレーション（V1〜V15）を `target` に残していたため。`scripts/api.mjs` の API のビルドに `clean` を付けて直した。直す前のフォルダーでは、`backend` で `mvnw clean package -DskipTests` を実行してから `setup.bat` を実行すると、空の DB にテーブルが作られる
- `scripts/setup.ps1` は、確認の処理を `scripts/database-verify.ps1` の関数の呼び出しに置き換えた。処理の中身は変えていない
