# 新しい DB（v3）の実装計画

元の場所：kusakari-canvas の未追跡ファイル docs/discussions/db-v3-implementation-plan.md（2026-11-16 に移動。Git の履歴はない）

2026-11-11 作成。[db-v3-design.md](../DB構成/2026-11-11_db-v3-design.md) の設計案を、EC と Canvas に実装するための計画です。

- 作業は、EC・Canvas それぞれの統合ブランチ `feature/shop-organization` から切ったブランチで行います。main にはマージしません
- 既存のデータは移行しません。開発用・E2E 用の DB は、初期化スクリプト（ec#106、canvas#63）で作り直します
- 起動時に DB を消す処理は作りません。初期化は、確認の入力が付いた手動のスクリプトだけが行います

## 1. 前提と、今の状態

| 項目 | 状態 |
| --- | --- |
| EC の DB の DDL | 使い捨ての MySQL 8.0.46 で作り、制約を79件確かめた（[db-v3-design.md](../DB構成/2026-11-11_db-v3-design.md) 7章） |
| Canvas の DB の変更 | 未確認 |
| アプリケーションからの動作 | 未確認（確かめたのは SQL だけ） |
| 設計案のうち、issue の決定から変えた9点 | 未承認（下の 2.） |

## 2. 着手の前に決めること

設計案は、互換性が不要という前提で、issue の決定から9点を変えています。実装の前に、採用するかを決めます。

| 番号 | 設計案 | issue での決定 | 採用しない場合 |
| --- | --- | --- | --- |
| 1 | 会員のテーブル名を `members` にする | `auth_members` を残す | 名前だけ戻す。ほかに影響しない |
| 2 | 出店申請のテーブル名を `organization_applications` にする | `store_applications` に列を足す | 名前だけ戻す |
| 3 | 店舗を `published`（オーナー）と `suspended`（運営）に分ける | `enabled` 1つで、初期値を非公開にする | 運営の停止を解除したときに、未公開の店舗が公開されない仕組みを別に作る |
| 4 | 組織の停止を `suspended` にする | `enabled` | 名前と真偽の向きだけ戻す |
| 5 | 受取連絡先と支払方法を `orders` に入れる | `order_details` を4列にして残す | テーブルを1つ足す |
| 6 | 緯度経度を NULL にできる | 未決定 | 緯度0・経度0 を「位置なし」として扱う処理を、店舗の案内にも入れる |
| 7 | 商品番号を `(store_id, sku)` で一意にする | `sku` で一意 | 店舗が違っても同じ商品番号を使えない |
| 8 | 会員に `email_verified_at` と `created_at` を足す | 指定なし | 14日での削除（ec#109）を判定する別の手段が要る |
| 9 | 招待キーから `organization_id` を外す | v2 の図にあり | 列を1つ足す |

あわせて、DB の形に影響する未決定事項が残っています。決まるまでは「仮の形」で進め、決まったらマイグレーションを直します（main に入れる前なので、直してよい）。

| 未決定事項 | 仮の形 | 決める場所 |
| --- | --- | --- |
| 招待キーは1回限りか、期限内なら何人でも使えるか | 1回限り | ec#105 |
| 料金プランを組織と店舗のどちらに持つか | 申請の行に残す | ec#125 |
| 同じ品種の商品をジャンルでまとめるか | 入れない | 未起票（[9.md](../商品とカート/2026-11-06_9_商品と店舗の関係.md)） |
| `material_products` を残すか | 残す | ec#119 |
| 認証基盤に残ったユーザーを初期化のときに消すか | 消さない前提で、初回ログインの処理を作る | ec#108 |

## 3. 進める順番

## 4. 確かめ方

- 段階2：マイグレーションで作った DB に、試験の79件を実行し直す。実際のテーブルが ER 図と一致していることを確かめる
- 段階3以降：実 API と MySQL を使う Chromium E2E で、各 issue の完了条件を確かめる。正常系で API をモックしない
- 開発中は、型確認・lint・ビルド・変更した範囲の E2E を実行する。全 E2E は段階6で実行する
- 試験は専用の DB で行い、開発者の DB では行わない

## 5. リスク

| リスク | 起きること | 備え |
| --- | --- | --- |
| 初期化の対象を間違える | 別のプロジェクトや開発者のデータが消える | 対象を特定できない・複数あるときは何も消さずに止める。消す前に対象を表示し、確認の入力を求める（ec#106、canvas#63） |
| 初期化で失われるもの | EC：今の会員・店舗・商品・注文。Canvas：庭・写真・画像生成の履歴 | 移行しないと決まっている（ec#102 決定事項2）。初期化の前に、必要ならバックアップを取る |
| EC と Canvas の片方だけを初期化する | 庭の持ち主と、EC の買い物リストが持つ庭 ID が食い違う | 2つの初期化を続けて実行する手順にする（ec#113） |
| 未決定事項が後から決まる | マイグレーションを直すことになる | main に入れる前は、マイグレーションを直して DB を作り直す |
| 同時実行を確かめていない | 同じ在庫の同時購入、同じ招待キーの同時使用で、想定外の結果になる | 在庫と招待キーの行をロックしてから更新する。段階4の E2E で確かめる |
| 途中の段階では画面が動かない | 段階2の後、段階3〜4が終わるまで、統合ブランチで一部の画面が動かない | 統合ブランチの中だけで進め、main には入れない |

## 6. この計画に含めないもの

- 発送（ec#120）、別の店舗の商品の複製（ec#121）、店舗の閉鎖（ec#79）、運営の警告（ec#16）
- 手数料の計算・請求、実決済、外部メール配信
- 統合ブランチを main に入れる時期と方法（ec#113 で決める）
